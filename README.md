# Erie Library System

A desktop library management application built with **Java Swing** and backed by a
**PostgreSQL** database (hosted on Supabase). Members can register, log in, browse the
catalog, borrow or buy books, return rentals, and track their account balance — all
through a graphical interface, with every action persisted to the database.

> Originally built as a final course project and since refactored from flat-file storage
> to a real relational database with a DAO layer.

---

## Features

- **Membership accounts** — register a new member or log in with existing credentials.
- **Browse the catalog** — see every book that currently has available copies.
- **Borrow (rent)** — the first **5 rentals per calendar month are free**; each rental
  beyond that adds a **$2.00** fee to the member's balance.
- **Buy** — purchase a book outright (no due date, no return).
- **Return** — return an active rental and free the copy back into the catalog.
- **Profile** — view membership details, current books, amount owed / paid, and pay off
  an outstanding balance.

│   ├── BookDAO.java        # BOOK table access: list, lookup, adjust copies
│   └── CheckoutDAO.java    # CHECKOUT table access: rent, buy, return, monthly counts

└── bin/                    # Compiled .class output

### How it fits together

`GUIBase` (the view) calls into the `Library` / `Regular` domain objects, which enforce the
borrowing rules and delegate all persistence to the DAO classes. The DAOs open connections
through `DBConnection` and run parameterized SQL against the PostgreSQL schema.

## Database Schema

The application expects the following tables (identifiers are **case-sensitive**, created
in upper case, so SQL must double-quote them):

- **`USER`** — `USER_ID`, `FNAME`, `LNAME`, `USERNAME`, `PASSWORD`, `MEM_TYPE`,
  `MONTHLY_FEE`, `AMOUNT_OWED`, `AMOUNT_PAID`, `CHECKOUT_DATE`, `DUE_DATE`
- **`BOOK`** — `BOOK_ID`, `TITLE`, `AUTHOR`, `SUBJECT`, `DATE_PUBLISHED`,
  `AVAILABLE_COPIES`, `BUY_PRICE`
- **`CHECKOUT`** — `CHECKOUT_ID` (identity), `USER_ID`, `BOOK_ID`, `ACTION` (`'rent'` /
  `'buy'`), `CHECKOUT_DATE`, `DUE_DATE`, `RETURN_DATE`, `AMOUNT_CHARGED`
- **`AUTHOR`** — `AUTHOR_ID`, `FNAME`, `LNAME`, `DATE_PUBLISHED`
- **`JOIN`** — `BOOK_ID`, `AUTHOR_ID`

> **Note on `CHECKOUT_ID`:** it is a `GENERATED BY DEFAULT AS IDENTITY` column. If you seed
> `CHECKOUT` rows with explicit IDs, remember to advance the identity sequence afterwards,
> or new inserts will collide:
> ```sql
> SELECT setval(pg_get_serial_sequence('"CHECKOUT"', 'CHECKOUT_ID'),
>               (SELECT MAX("CHECKOUT_ID") FROM "CHECKOUT"));
> ```

## Configuration

Database credentials live in `src/DBConnection.java`:

```java
private static final String URL      = "jdbc:postgresql://<host>:5432/<database>";
private static final String USER     = "<db-user>";
private static final String PASSWORD = "<db-password>";
```

Fill in your own PostgreSQL/Supabase connection details before running.

> ⚠️ **Do not commit real credentials.** Replace them with placeholders (or read them from
> environment variables via `System.getenv(...)`) before pushing to GitHub. See
> [Security](#security) below.

## Getting Started

### Prerequisites

- Java 17 or newer (JDK)
- A reachable PostgreSQL database with the schema above
- The bundled JDBC driver in `lib/` (already included)

### Compile

```bash
javac -cp "lib/postgresql-42.7.4.jar" -d bin src/*.java
```

### Run

The JDBC driver must be on the classpath (use `;` instead of `:` on Windows):

```bash
java -cp "bin:lib/postgresql-42.7.4.jar" GUIBase
```

Then **Register** a new account, and log in with it to reach the dashboard.

## Security

This project connects to a live database, so keep secrets out of version control:

- **Never commit real database credentials.** Use placeholders in `DBConnection.java`, or
  load them from environment variables.
- The included `.gitignore` excludes the `bin/` build output and legacy `*.txt` account
  files (from the earlier file-based version, which stored usernames and passwords in
  plain text).
- If a real password is ever pushed, **rotate it** — Git history keeps it even after deletion.

Example `.gitignore`:

```gitignore
bin/
*.txt
.DS_Store
```

## Lessons Learned

Migrating this project from flat-file storage to a live PostgreSQL database surfaced a
series of real-world issues. Each one below is something the project actually hit and had
to fix:

### 1. Keep the model and its callers in sync when refactoring
Moving from files to a database changed method signatures and constructors (e.g. `Book`
gained `incrementCopies()` / `decrementCopies()`, and `Regular` gained a constructor that
also carries balances). Callers that weren't updated caused *"method/constructor
undefined"* compile errors. **Takeaway:** when you change a class's public shape, compile
the whole project — the compiler is your checklist for every caller you still need to
update.

### 2. A JDBC driver has to be on the runtime classpath, not just imported
Running with only `-cp bin` produced:
```
java.sql.SQLException: No suitable driver found for jdbc:postgresql://...
```
The PostgreSQL driver is a separate JAR — importing `java.sql.*` isn't enough. **Takeaway:**
the driver JAR must be on the classpath at runtime (`-cp "bin:lib/postgresql-42.7.4.jar"`),
and in VS Code it must be listed under `java.project.referencedLibraries`.

### 3. Read the exception message — the layer it fails at tells you the cause
The errors walked us through the stack one layer at a time: *no driver* → *authentication
failed* → *column does not exist* → *duplicate key*. Each new message meant the previous
problem was actually fixed. **Takeaway:** a *different* error after a change is progress,
not failure.

### 4. Placeholder credentials fail loudly
```
FATAL: password authentication failed for user "postgres"
```
`DBConnection.java` still held `YOUR_REAL_PASSWORD_HERE`. **Takeaway:** connection failures
are often configuration, not code — check the credentials before debugging the query.

### 5. PostgreSQL folds unquoted identifiers to lower case
This was the biggest one. The tables were created with **upper-case** names
(`USERNAME`, `AMOUNT_OWED`, `AVAILABLE_COPIES`, `ACTION`, ...), but the SQL referenced them
unquoted and lower-case:
```
ERROR: column "username" does not exist
```
Postgres lower-cases any identifier that isn't double-quoted, so `username` never matched
the real `USERNAME` column. **Takeaway:** if a table/column is created with quotes or in a
non-lowercase case, *every* reference to it must be double-quoted with the exact same case
— `WHERE "USERNAME" = ?`, not `WHERE username = ?`. (The simpler long-term habit is to
create all identifiers in lower case so quoting is never needed.)

### 6. Seeding rows with explicit IDs desyncs an identity/serial sequence
Borrowing failed with:
```
duplicate key value violates unique constraint "CHECKOUT_pkey"
Detail: Key ("CHECKOUT_ID")=(1) already exists.
```
`CHECKOUT_ID` is `GENERATED BY DEFAULT AS IDENTITY`, but the seed rows were inserted with
explicit IDs (1–12), which does **not** advance the underlying sequence — so the next
auto-generated ID started back at 1 and collided. **Takeaway:** after bulk-loading rows
with explicit primary keys, reset the sequence to the current max:
```sql
SELECT setval(pg_get_serial_sequence('"CHECKOUT"', 'CHECKOUT_ID'),
              (SELECT MAX("CHECKOUT_ID") FROM "CHECKOUT"));
```

### 7. Separating concerns paid off
Because persistence lived in DAO classes (`MemberDAO`, `BookDAO`, `CheckoutDAO`) rather
than inside the UI, every fix above was localized to SQL in one small file — the Swing code
never had to change. **Takeaway:** a thin data-access layer makes database problems easy to
find and cheap to fix.
